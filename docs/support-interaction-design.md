# 通用客服的结构化交互与生成式 UI

日期：2026-10-24。状态：首个补资料交互闭环已实现，包括结构化工具参数、CLI 展示、CopilotKit 页面及同会话提交。本文记录设计依据；实际装配、存储字段、测试与边界见 [实现记录](iterations/information-ui.md)。操作确认属于后续 G 阶段。

## 1. 具体问题与本次范围

用户只描述“导出失败了”时，客服需要收集环境、错误信息和复现过程。目前只能用普通文本追问，无法为未来页面提供可校验的交互规格。目标是让同一个 Agent 根据问题提出表单，客户端用已有组件渲染，用户提交后继续同一会话。

通用性放在交互机制上：文本、补充信息、工具执行结果、受控操作确认。各业务的订单、金额、任务字段由实际接入能力定义，不提前加入平台的统一回复 schema。

设计前已有普通文本流、节点更新、PostgreSQL checkpoint、身份范围和三项内部记忆工具。现已新增表单工具、应用持久交互状态、同会话提交和本地 CopilotKit 调试入口；业务登录及生产部署尚未实现。实际源码以 `apps/agent/src/agent/agent.ts`、`run.ts` 及 [实现记录](iterations/information-ui.md)为准。

原计划将工具/CLI、协议适配及页面提交分别推进；后续用户已授权结构化输出和生成式 UI，现已完成这三个环节的最小开发闭环。普通聊天仍可只输出文本，不要求每轮创建表单，也不新增模型分类调用。

## 2. 三类结构分别负责什么

| 结构 | 谁产生 | 谁消费 | 信任边界 |
| --- | --- | --- | --- |
| 模型提出的交互规格 | 模型通过 `request_information` 工具参数产生 | 工具校验器、前端组件 | 只是请求补资料，不含身份、执行权限或实际操作结果 |
| 服务端交互记录与事件 | 应用绑定本轮上下文后产生 | CLI、将来的 UI 和提交入口 | ID、归属、版本和状态由程序管理，不能让模型或浏览器决定 |
| 业务任务的最终结构化结果 | 按实际任务另定 `responseFormat` / schema | 需要这些字段的业务消费者 | 格式有效不代表事实正确；本次不强制加入 |

选择“文本流 + 有类型的交互工具参数/结果”。`request_information` 是真实的客服交互能力，其成功只代表创建了补资料请求，不代表用户已填写或问题已解决。

## 3. 模型生成的第一份工具参数契约

以下是建议形状；实现时由 Zod 定义并推导 TypeScript 类型。不是让模型生成组件代码。

```ts
type FieldBase = { key: string; label: string; required: boolean };

type InformationField =
  | (FieldBase & { type: "text" | "textarea" })
  | (FieldBase & {
      type: "select";
      options: Array<{ value: string; label: string }>;
    });

type InformationRequestSpec = {
  title: string;
  description: string;
  fields: InformationField[];
};
```

模型按需填写的例子：

```json
{
  "title": "补充问题信息",
  "description": "请提供使用环境和错误现象，方便继续排查。",
  "fields": [
    {
      "key": "environment",
      "type": "select",
      "label": "使用环境",
      "required": true,
      "options": [
        { "value": "windows", "label": "Windows" },
        { "value": "macos", "label": "macOS" },
        { "value": "browser", "label": "浏览器" },
        { "value": "other", "label": "其他" }
      ]
    },
    {
      "key": "symptom",
      "type": "textarea",
      "label": "报错内容或具体表现",
      "required": true
    }
  ]
}
```

环境选项是本轮提问内容，不是平台固定支持的产品或系统清单。`key` 是本表单的字段标识，不是数据库列名、业务 API 参数或权限标识；不能直接把字段答案展开为业务工具参数。

建议首版边界均写在代码中：

| 项目 | 约束 |
| --- | --- |
| 标题与说明 | 标题 1–80 字符，说明 1–500 字符 |
| 字段 | 1–6 项，key 为字母开头的字母/数字/下划线，最多 40 字符，表单内唯一 |
| 标签 | 1–120 字符；作为纯文本显示 |
| 选择项 | 2–10 项；value 唯一且最长 80 字符，label 最长 120 字符；只允许 select 携带 options |
| 用户文本答案 | text 最长 500 字符，textarea 最长 2000 字符；必填 trim 后不能为空 |
| 用户选择答案 | 必须属于服务端保存的选项，拒绝额外字段或未知 key |
| 对象形状 | 各层 strict 校验；拒绝未知控件、未知属性和重复 key |

首版不提供文件上传、密码控件、任意 URL、HTML、脚本、事件处理代码或模型自定义正则。提示词明确不索要密码、验证码、密钥等凭据；这不能保证模型标签语义一定安全，仍需真实语料回归与既有 PII/凭据处理。提交内容在进入后续 Graph、追踪和应用存储前执行对应的数据最小化策略，不直接记录原始请求体。

## 4. 服务端补全的结构

模型只接触第 3 节的规格。以下字段由程序生成、绑定或更新：

| 字段 | 用途 |
| --- | --- |
| `schemaVersion` | 首版为 1，标识公开交互契约版本 |
| `formId` | 服务端生成的不透明交互 ID，不作为访问授权 |
| `formVersion` | 表单规格版本，提交必须匹配 |
| `createdRunId` / `toolCallId` | 关联创建本表单的实际运行/工具调用，用于追踪及去重 |
| `threadId` / `ownerScope` | 绑定真实会话与 SupportContext 范围；ownerScope 留在服务端 |
| `spec` | 完整校验后的表单规格 |
| `status` | `draft`、`pending`、`submitted`、`expired` 或 `invalidated` |
| `expiresAt` | 服务端时间；首版建议有效期 30 分钟，策略写在代码中 |

不要求模型复制 runId、用户 ID 或其他可信关联字段。`request_information` 的工具结果可以返回 `{ status: "created", formId, formVersion, spec }`；created 是创建结果，不是已提交状态。

创建阶段为 draft。首版仅在创建轮正常完成后开放提交；失败/超限的创建轮将其作废。前端可以展示准备中的卡片，但未完整校验、未获准提交的卡片不可点击。`run.ts` 的 Graph 节点更新不等于表单已创建或业务操作成功。

## 5. 提交与继续对话：目标闭环

1. 用户提问 → 现有输入脱敏、SupportContext、checkpoint、记忆流程。
2. 模型选择普通回答，或调用 `request_information(spec)`；参数经过 schema 和数量约束校验。
3. 应用绑定真实上下文，持久保存交互规格、创建标识和 draft 状态；通过程序生成的交互事件提供展示数据。工具返回只表示创建完成。
4. 模型继续输出说明，本轮正常结束；应用将本轮有效表单开放为 pending。
5. 用户填写并提交 `{ formId, formVersion, submissionId, answers }`。浏览器不上传自己的表单 schema、身份或执行状态来替换服务端记录。
6. 服务端按认证上下文读取表单，检查归属、版本、有效期、pending 状态和答案规格；原子地接受提交并记录结果。
7. 根据保存的标签和校验后的答案生成一条用户补充消息，进入同一会话的下一轮。答案属于用户数据，不提升为系统提示词，也不等于同意业务操作或同意永久记忆。

这是“本轮结束 → 用户补资料 → 下一轮”的流程。不是尚未返回的工具调用，不伪造 ToolMessage，也不需要为普通追问引入 interrupt/resume。

正常新问题到来时令之前未提交表单失效，首版同一会话只允许一个当前可提交表单；并行提出多份表单时明确拒绝或作废冲突请求，不任取一份。提交原子性不能仅靠前端禁用按钮或 checkpoint 快照保证，应用持久层需要支持状态比较与幂等写入；具体存储在提交闭环切片中实现并验证，不把第一步的工具输出宣称为已经具备可靠提交能力。

同一 submissionId 和相同内容重复提交返回原处理状态，不再次触发 Agent；相同 ID 不同内容拒绝。用户修改已提交内容须重新发起新输入。接受提交、启动下一轮和模型完成不是同一件事：中途崩溃/超时可能留下已接受但执行未完成的状态，需可查询，不自动重放；首版不宣称恰好执行一次或具备后台恢复队列。

## 6. 失败行为

| 情况 | 对外行为 |
| --- | --- |
| 模型规格缺字段、重复 key、未知控件 | 不创建可提交表单；首版明确反馈校验失败，不无限修复 |
| 创建存储失败或超时 | 不返回已创建成功；保留安全诊断，结果未知时不自动重试 |
| 创建后本轮模型断流/超限 | 本轮失败，表单不可提交；之前文本不当作完整结果 |
| UI 未支持版本或组件渲染失败 | 显示安全的文本追问，禁用交互；不暴露原始工具参数/错误 |
| 提交字段不合法 | 返回字段级错误，保留用户当前填写内容，不调用模型 |
| 表单过期、失效或版本不匹配 | 提示重新发起补资料，旧卡片不能执行新轮次操作 |
| 不存在或归属不符 | 使用统一的不可用错误，不泄露其他用户是否存在此表单 |
| 重复提交 | 返回原提交状态，不产生重复用户消息或新的模型调用 |
| 接受提交后模型失败 | 明确区分已接收资料和本轮回答失败，不假装提交未发生、不自动续跑 |

用户也可以直接用普通文本回答问题，不强制填写卡片。文本追问降级只有在程序持有有效规格时才能从该规格生成；未通过校验的模型数据不直接渲染。CLI 没有控件时把有效规格格式化为可读问题，仍走现有下一轮文本输入。

## 7. 操作能力的扩展边界

补资料表单不能执行退款、重试任务等操作。未来业务登记独立工具，分别定义参数、返回值、身份与执行规则；查询事实由工具提供，模型组织答案。

写操作按“提议 → 服务端准备/校验 → 用户确认 → 业务侧再次校验并执行 → 展示真实结果”推进。操作卡片引用服务端 actionId，绑定用户、会话、参数版本和有效期；更改参数须重新确认。点击卡片不直接调用模型填写的 URL，也不跳过业务规则。

运行中、成功、失败和结果未知来自真实执行记录，不能来自模型声称的 status。宿主页面跳转/填草稿使用单独的前端白名单能力；不当成后台业务执行成功。操作确认与执行尚未实现，本次不加入空壳动作注册平台。

## 8. 官方机制、替代方案与选择

官方机制已于 2026-10-24 在本轮会话核对：

- [LangChain 结构化输出](https://docs.langchain.com/oss/javascript/langchain/structured-output)：responseFormat、toolStrategy/providerStrategy 和最终 structuredResponse；用于真正需要最终任务结果的场景，不是所有 UI 的唯一入口。
- [CopilotKit 组件作为工具](https://docs.copilotkit.ai/langgraph-typescript/generative-ui/display)：预定义组件接收结构化参数。
- [CopilotKit 工具调用渲染](https://docs.copilotkit.ai/langgraph-typescript/generative-ui/tool-rendering)：自定义组件展示工具参数、状态和结果。
- [CopilotKit 与 LangGraph](https://docs.copilotkit.ai/langgraph-typescript)：现有 Agent 经服务/AG-UI 适配接入；不能把本地 createAgent 对象直接视为可用浏览器服务。

这些是官方支持的机制，不是行业占有率或性能结论。产品锁定 langchain 1.5.18、langgraph 1.5.2、zod 4.6.7；已接 CopilotKit 1.79.1 / AG-UI 1.0.2，应用自行适配已有 runSupportAgent，持久化仍归现有应用管理。不用另一个 BuiltInAgent 替换当前 Agent，也不复制学习仓库的教学运行时。

| 方案 | 取舍及何时改用 |
| --- | --- |
| 普通文本追问 | 仍保留，最低交互成本；CLI 和渲染失败可使用，但不提供可校验表单 |
| 交互工具 schema + 文本回答 | 当前选择；复用真实工具循环和既有文本流，额外工具及后续模型步骤计入现有预算 |
| 每轮完整最终 JSON | 本次不强制；会改变当前文本投影，可能要等完整结构才能展示。出现明确的最终业务结果消费者时按任务启用 |
| 组件目录/声明式布局 | 当前只提供少量控件；出现真实复杂展示需求后扩展，不先开发通用页面 DSL |
| 自由生成页面代码 | 需要独立隔离和执行边界，当前客服流程没有采用需求 |
